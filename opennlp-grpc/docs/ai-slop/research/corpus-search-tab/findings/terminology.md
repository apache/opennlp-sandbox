# Corpus search: every user-visible term, and whether it is standard

Scope: every string a user can read on the Corpus search tab (`#server-search`,
index.html:546-720, plus the strings generated by `src/server-search-workbench.ts`,
`src/search-view-model.ts`, `src/query-builder.ts`).

Verdicts come from `../reference/terminology-*.md` (fetched 2026-08-28). FACT rows describe the
string and its precedent; OPINION rows carry a priority.

## 1. Query controls

| String (location) | Verdict | Precedent, or nearest standard term |
| --- | --- | --- |
| "Search index" (label, index.html:587) | STANDARD | Every engine; the compound noun is unambiguous next to a select |
| "Natural-language query" (index.html:595) | STANDARD ENOUGH | No vendor uses it verbatim, but it correctly signals "not a syntax". Elastic's equivalent is a `semantic` query over `semantic_text` |
| "Results" as the label of the top-k number input (index.html:600) | NONSTANDARD | Every engine names this count `hits` (Lucene `TopDocs.totalHits`, Elasticsearch `hits`, Algolia `hitsPerPage`/`nbHits`, Typesense `hits`). This tab itself calls each row a "hit" ("0 hits", server-search-workbench.ts:287), so the input and the counter disagree |
| "Search index →" (button, index.html:603) | STANDARD | Solr Admin's equivalent is "Execute Query" |
| "Semantic" clause kind (index.html:615) | STANDARD | Elasticsearch ships a query type literally named `semantic`; peers name the mechanism instead (Vespa `nearestNeighbor`, Weaviate `nearText`) |
| "Term" clause kind (index.html:616) | STANDARD | Lucene `TermQuery`; Elasticsearch `terms` query |
| "Phrase" clause kind (index.html:617) | STANDARD | Lucene `PhraseQuery`; Elasticsearch `match_phrase` |
| "Match any term" / "Match all terms" (index.html:623-624) | PLAIN ENGLISH, NONSTANDARD WORDING | The products expose this as `operator: OR` / `AND` (Elasticsearch `match`), `q.op=OR/AND` (Solr), or `minimum_should_match`. The meaning maps one to one, so the wording is friendlier than the standard and not wrong |
| "Phrase slop" (visually hidden label, index.html:626-627) | STANDARD | `slop` is the literal parameter name in Lucene `PhraseQuery` and Elasticsearch `match_phrase`; Solr writes it `"a b"~10`. It is standard AND opaque: no vendor explains it in a UI either |
| "Add clause" / "Clear clauses" (index.html:629, 637) | STANDARD | "clause" is Lucene and Elasticsearch `bool` vocabulary |
| "Join" (select label, index.html:632) | NONSTANDARD IN THIS SENSE | In search products "join" means a cross-index join (Solr `{!join}`, Elasticsearch `has_child`). The standard word for what this select does is *operator* or *combine* |
| "All clauses (AND, mean score)" (index.html:633) | BEHAVIOUR IS THIS PROJECT'S OWN | Accurate to `opennlp_query.proto:128-129` ("score is the mean of operand scores"), but Lucene and Elasticsearch `bool` **sum** the scores of matching clauses. A reviewer from Elasticsearch will read "mean" as a bug until they check |
| "Any clause (OR, maximum score)" (index.html:634) | STANDARD BEHAVIOUR, UNUSUAL NAME | Maximum-of-clauses is the *dismax* convention: Lucene `DisjunctionMaxQuery`, Solr `dismax`/`edismax`, Elasticsearch `dis_max` with `tie_breaker`. Plain `bool.should`, which most users read as "OR", sums instead |
| "Any clause, reciprocal-rank fusion" (index.html:635) | STANDARD | Cormack, Clarke and Buettcher, SIGIR 2009; Elasticsearch `rrf` retriever; OpenSearch `score-ranker-processor` `"technique": "rrf"`; Vespa `reciprocal_rank_fusion`. Note every product exposes the rank constant `k` (default 60); this UI does not |
| Clause chips "semantic: X", "term (any): X", "phrase (slop 0): X" (`src/query-builder.ts:58-68`) | STANDARD | Compact and consistent with the clause vocabulary above |

### OPINION (P2): fix the two count words

Rename the top-k input label from "Results" to **"Hits"** (index.html:600) so it matches
`#server-result-count` ("0 hits", server-search-workbench.ts:287) and every engine's vocabulary, or
rename the counter to "results" and use that everywhere. Two words for one concept on one screen is
the avoidable half of this.

### OPINION (P2): "Join" and the score algebra

Rename the `#builder-join` label from "Join" to **"Combine clauses"** and move the score algebra out
of the option text, as proposed in `naming-alternatives.md` section 4. Then add one sentence saying
the AND score is a mean and the OR score is a maximum, so a reader who expects Elasticsearch's sum
sees the difference stated rather than inferred.

## 2. Scores and the legend

| String (location) | Verdict | Precedent |
| --- | --- | --- |
| "cosine score" with a −1 to +1 legend (index.html:558-561) | METRIC STANDARD, DISPLAY UNUSUAL | Cosine is standard everywhere. Showing the raw −1..+1 range is not: Elasticsearch rescales to `(1 + cosine) / 2` because "Lucene requires scores be positive or 0"; Weaviate shows `distance` (0..2) or `certainty`. Qdrant is the one product that returns raw cosine in −1..1, so there is precedent, just not the majority one |
| "less similar / more similar" captions (index.html:561) | GOOD PRACTICE, NO VENDOR PRECEDENT | No engine explains its score scale in the UI at all. Keep this |
| "Cosine score" inspector fact to six decimals (server-search-workbench.ts:474) | STANDARD | Elasticsearch `_score`, Solr `score` |
| "similarity" caption under the selected score (index.html:671) | STANDARD | Weaviate and Qdrant both say similarity |
| "No score" placeholder (index.html:671) | FINE | |

FACT. The front end enforces the legend's range: `readSearchResponse` drops any hit whose score is
outside [−1, 1] (`src/search-adapter.ts:270`), and `scoreColor` clamps
(`src/search-view-model.ts:60`). So the legend is not decorative, it is the contract.

## 3. Results, evidence, and the inspector

| String (location) | Verdict | Precedent |
| --- | --- | --- |
| "hit" / "hits" (server-search-workbench.ts:287, index.html:655) | STANDARD | Lucene `TopDocs`, Elasticsearch `hits.hits`, Algolia `nbHits`, Typesense `hits` |
| "Ranked evidence" / "Selected evidence" (index.html:649, 670) | INVENTED | No vendor uses "evidence" for search results. It is, however, an honest description of what this panel does and reads well. Retrieval-evaluation literature does speak of evidence for a claim |
| "Search results" / "Result inspector" (index.html:649, 670) | STANDARD | |
| "chunk" (throughout: "scored chunks", "Indexed chunk", "Chunk ID") | STANDARD, CURRENT | Elastic's `semantic_text` docs use "chunk" and `chunking_settings` and speak of retrieving indexed chunks. The retrieval literature word is "passage" (MS MARCO, TREC Deep Learning, Vespa passage ranking); "fragment" is reserved for highlight units (`fragment_size`). This UI uses "chunk" consistently, which is the right choice |
| "Heatmap" view toggle (index.html:653) | LABEL REPURPOSED | The visualization itself has a well-known ancestor, Hearst's TileBars (CHI 1995): "the darkness of a square indicates the frequency of query terms in the segment". But in search products "heat map" means a matrix chart (Kibana's heat map aggregation), and no engine ships per-passage score shading. See the OPINION below |
| "matched span" / `<mark class="matched-span">` and the tooltip "Matched query term: X" (server-search-workbench.ts:395, 528) | CONCEPT STANDARD, LABEL INTERNAL | The user-facing word is **highlight**: Elasticsearch `highlight` returns "best-matching highlighted snippets", Solr `hl`, Algolia `_highlightResult` with `matchedWords`, Typesense `highlights` with `matched_tokens`. "Matched span" is correct Lucene-level vocabulary (`Matches`, `SpanQuery`) but is not consumer-facing anywhere |
| "Authoritative source" and "Selected span is painted with its fixed score color." (index.html:684-685) | INVENTED, CLEAR | No precedent, but it names a genuine distinction this product makes and competitors do not: the stored original versus the normalized indexed text |
| "Original source span" / "Indexed chunk" (index.html:694, 698) | INVENTED, CLEAR | Same |
| "The indexed chunk exactly matches the original source span, so it is shown once." / "...differs from the original span, usually because normalization was applied before indexing." (server-search-workbench.ts:456-460) | GOOD | Explains the collapse instead of leaving a silent one-panel layout |
| "Sentences / Tokens / Entities / Chunks / Terms" (index.html:674-680) | STANDARD | Core OpenNLP vocabulary |
| "Annotations covering this chunk" (index.html:712) | STANDARD IN NLP | "annotation" and "layer" are UIMA and OpenNLP vocabulary, not search vocabulary. Correct for this audience |
| "Source offsets 12..40 (UTF-8 bytes)" (server-search-workbench.ts:473, `offsetLabel` at 630-638) | STANDARD, PRECISE | Naming the encoding is unusual and correct: the front end refuses hits whose offsets do not decode (`src/search-adapter.ts:266-268`) |
| "The server response byte limit truncated additional matches." (search-view-model.ts:96-98) | NONSTANDARD WORD | The standard signal is a total-count relation: Elasticsearch `hits.total.relation: "gte"` with `track_total_hits`, Solr `numFoundExact=false`. "Truncated" is clearer than either, so this is a case where the invented word is better |

### OPINION (P3): "Heatmap"

Keep the word. It is the term a general audience already attaches to "shading by intensity", the
ancestor visualization is real prior art, and the alternative names ("relevance shading",
"per-chunk score") are less recognizable. Do add the one clarifying phrase the panel currently
lacks in its heading: the empty state explains it ("shade every chunk of every document",
index.html:663-664) but the toggle button is bare.

### OPINION (P3): consider "highlighted" over "matched span" in user-facing copy

The builder intro already says "keyword matches return highlighted spans" (index.html:610-611),
which is the right word. The tooltips say "Matched query term". Aligning both on "highlight" would
match Elasticsearch, Solr, Algolia and Typesense at once. Low value, low risk.

## 4. Provenance vocabulary in the inspector

FACT. The "Identity and provenance" list (index.html:706) can render up to nineteen facts
(`server-search-workbench.ts:471-510`): Document ID, Chunk ID, Source offsets, Cosine score, Index,
Search provider, Configured embedding route, Query embedding route, Corpus, Provenance, Model
artifact, Query model artifact, Corpus artifact, Index bundle, Bundle format, Index builder,
Preparation config, Corpus license, Source.

| Term | Verdict | Precedent |
| --- | --- | --- |
| "Provenance" | STANDARD, but from outside search | W3C PROV. No search vendor shows provenance in a result panel |
| "Corpus" | STANDARD in IR literature | Product UIs say index or collection |
| "vector space" (in the route labels, `configuredRouteLabel`, server-search-workbench.ts:617-619) | STANDARD AS A CONCEPT | Salton's vector space model (1975); Vespa uses the phrase. Not used as an inspector label anywhere |
| "embedding route" | INVENTED | Nearest vendor terms: Elasticsearch `inference_id` and inference endpoints, Vespa "embedder", Weaviate "vectorizer" |
| "Model artifact" / "Corpus artifact" / "artifact hash" | INVENTED for a search UI | The documentation convention for exactly this identity information is model cards and dataset cards |
| "None (keyword-only query)" for the query route (server-search-workbench.ts:625) | GOOD | States plainly why a field is empty instead of leaving it blank |
| "Search provider" rendered as "turbo quant" / "flat float" / "terms" (`providerLabel`, server-search-workbench.ts:645-648) | PROJECT VOCABULARY | The enum shorthand is lowercased and underscore-stripped, so `STANDARD_SEARCH_PROVIDER_TURBO_QUANT` becomes "turbo quant". "TurboQuant" is the product spelling used everywhere else in the UI (index.html:747, 1044) |

### OPINION (P3): "turbo quant" should read "TurboQuant"

`providerLabel` (server-search-workbench.ts:645-648) lowercases the enum and replaces underscores,
producing "turbo quant" and "flat float". Elsewhere the same two things are spelled "TurboQuant
(quantized)" and "Flat float (exact)" (index.html:747-748). A small display map would make the
inspector agree with the rest of the app.

### OPINION (P2): the inspector is the tab's best feature and its vocabulary is the least standard

Nothing here is wrong, and the provenance chain (corpus digest, bundle digest, builder identity,
preparation digest, embedding route) is genuinely more than any competitor exposes. The risk is
that a newcomer meets five invented compound nouns before they meet one familiar one. A single
sentence above the list, for example "Everything needed to reproduce this result: which corpus,
which model, which build", would frame it. That is cheaper than renaming the fields, and the field
names are precise.

## 5. Standard terms a search user will look for and not find

FACT (from `../reference/terminology-lexical-clauses.md` and
`../reference/terminology-vector-and-hybrid.md`). None of the following words appear anywhere on
this tab:

| Missing term | Standard meaning | Present in this product? |
| --- | --- | --- |
| **filter** | A clause that restricts the candidate set without contributing to the score (Elasticsearch `bool.filter`, Solr `fq`, Qdrant "Filtering", Typesense `filter_by`, Meilisearch filter expressions). The single most portable word in the industry, in seven of the ten products surveyed | YES in the protocol: `CelFilterClause` (`opennlp_query.proto:76`), a CEL predicate over document metadata. NOT exposed by the builder |
| **boost** | A multiplier on a clause's contribution (Elasticsearch `boost` and `boosting` query, Solr `term^4`) | YES in the protocol: `BoostClause` with a static `weight` or a CEL calculator (`opennlp_query.proto:74, 145-153`). NOT exposed by the builder |
| **hybrid search** | Combining lexical and vector retrieval in one query (Elasticsearch `rrf` retriever, OpenSearch `hybrid` query, Weaviate `hybrid` with `alpha`, Qdrant prefetch plus fusion) | YES: this is exactly what a semantic clause joined with a term clause does. The UI never says the word |
| **kNN** | Vector nearest-neighbour retrieval with `k` (Elasticsearch `knn` with `k` and `num_candidates`, Vespa `nearestNeighbor` with `targetHits`) | YES, as the semantic clause and the top-k field. Never named |
| **rerank** | A second, more expensive scoring pass over a candidate list (Cohere Rerank, Elasticsearch `text_similarity_reranker`, Vespa `global-phase` with `rerank-count`) | NO. Worth stating plainly: reciprocal rank fusion is not reranking. Fusion is cheap and rank-based; reranking rescores with a model |
| **facet** | Counts of matching documents grouped by a field, used to build navigation (Solr's original definition, Elasticsearch aggregations, Algolia `facetFilters`, Typesense `facet_by`) | NO, and there is no protocol support either |
| **fuzzy** | Edit-distance matching (Elasticsearch `fuzziness`, Solr `roam~1`) | NO |
| **BM25** | The default lexical scoring function | Keyword scoring exists; the function is not named in the UI. The optional Lucene add-on is described as "BM25-scored term and phrase execution" in README.md:119-122 |

### OPINION (P1): say "hybrid search" once

The tab already performs the thing the whole industry currently markets under that name, and it
never uses the phrase. One clause in the advanced-search intro ("this is hybrid search: keyword and
meaning in one ranked list") would connect the feature to what a visitor already knows. It costs
one sentence and it is accurate.

### OPINION (P2): the builder exposes three of the protocol's seven clause kinds

`QueryNode` (`opennlp_query.proto:63-80`) has seven cases: `semantic`, `term`, `phrase`, `join`,
`boost`, `cel_filter`, `cel_calculator`, and `JoinClause` additionally carries `exclusions`
(`opennlp_query.proto:119-120`, "Candidates matched by any exclusion are removed"). The builder
(`src/query-builder.ts:20-24`) models only semantic, term and phrase, and `buildQueryNode` never
emits `exclusions`, `boost`, or either CEL clause. Filter and boost are the two most requested
capabilities in every product surveyed and they already exist on the wire. Exposing at least NOT
(exclusions) would also let the UI use the third word of the boolean triple it already half uses.

## Questions for the lead

1. Is the −1..+1 cosine display a deliberate stance? It is defensible and Qdrant does it, but it
   differs from Elasticsearch's rescaled 0..1 and from Weaviate's certainty, so a visitor may read a
   0.2 here as a much worse match than the same document would show elsewhere.
2. Should the builder gain exclusions (NOT), filter, and boost, or is the intent to keep the visual
   builder deliberately minimal and point advanced users at the API?
