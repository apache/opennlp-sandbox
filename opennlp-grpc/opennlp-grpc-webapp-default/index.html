How to use the analyzer
  1. Paste a document (or press Load Alice novel), pick a preset, and choose an embedding model if you want vectors attached to the output.
  2. Press Analyze text. The complete typed response renders as the Document, Chunks, Heatmap, Graph, and Protobuf JSON views; select any annotation to inspect its exact span and payload.
  3. Press Add to live index to index the analyzed document, then query it from the Live index search tab.

From code this is one AnalyzeDocument gRPC call, or POST /api/v1/analyze on this gateway; Copy JSON and Download .pb export exactly what your client receives. Runnable Python, Node.js, Java, and Go quickstarts live in the repository's examples/ directory, and any other gRPC language generates a client straight from the opennlp-grpc-api protos.

    Text to searchable knowledge

    Build and explore in one flow

    Paste a small corpus and OpenNLP will analyze it, learn its vocabulary, distill a static embedding model, build a live index, and search it. Every stage stays visible.

    Checking this server
    What this tab builds

    An index is a searchable copy of your documents. The server splits each document into chunks, turns each chunk into a vector with an embedding model, and keeps the vectors so it can rank them against a question.

    With a teacher model installed, this tab builds one from scratch in six steps: it reads your documents, collects the words they use into a vocabulary, distils a small embedding model for exactly that vocabulary from the teacher, re-reads the documents through the new model, loads the result into a live index in server memory, and runs your first search against it. Without a teacher it still analyzes, indexes and searches, embedding with a model the server already has.

    A live index lives in memory and is gone when the server restarts unless you save it on the tab. The vocabulary and the distilled model are written to the server's artifact store and stay there. The index is listed on and on Lifecycle as soon as it is built.

    How to use corpus search
    1. Pick a configured index; its size, dimensions, and provenance appear beside it.
    2. Type a natural-language query. The server embeds it, ranks every candidate chunk by cosine similarity, and returns the scored results; the browser never ranks.
    3. Switch between the ranked list and the heatmap, which shades each returned chunk over the original document text on the fixed score scale above.
    4. Open a hit to compare the indexed (normalized) chunk with its original source span, and to browse the typed OpenNLP annotations for that document.
    5. Need exact words or phrases too? Open Advanced search below to combine phrase, keyword, and semantic clauses in one request.

    From code this is SearchIndex on OpenNlpSearchService, or POST /api/v1/search with a document-shaped query; GET /api/v1/search-indexes lists what you can search.

    What is a live index?

    A live index is one search index that this server builds in its own memory from documents you analyze on the Analyze tab. You can search it as soon as the first document is added, and you can keep adding documents to it.

    A live index has three states:

    • In memory: on the server only. It is gone when the server restarts.
    • Saved to disk: a copy is on the server's disk, and it still accepts new documents. Use Save to disk on the Lifecycle tab.
    • Read-only: on disk and closed to new documents. It stays searchable here and on the Corpus search tab.

    Elsewhere you may see this called a live index (Elasticsearch calls the writable member of a data stream the write index) or a collection (Qdrant, Weaviate, Solr). In this workbench a collection means something else: a group of live indexes whose vocabulary coverage the server watches on the Lifecycle tab.

    How to use live index search
    1. On the Analyze tab, analyze a document with an embedding model selected.
    2. Choose the vector storage above, exact flat float or quantized TurboQuant, then press Add to live index there. The first add creates a new live index in server memory.
    3. Describe what you want to find; the server embeds the query and returns ranked chunks with their source spans.
    4. To keep a live index across restarts, or to make it read-only, alias, or rebuild it, use the Lifecycle tab.

    From code this is IndexDocuments then SearchIndex, or POST /api/v1/index-documents and POST /api/v1/search; the Python, Node.js, Java, and Go quickstarts in examples/ run exactly this flow.

    Vocabulary to model

    Trainer

    Import a dictionary, learn a vocabulary from your documents, and distill a configured teacher into a static embedding model this server serves immediately.

    How to use the trainer
    1. Optionally import a dictionary; its headwords become guaranteed terms of every vocabulary learned afterwards.
    2. Paste corpus documents and learn a vocabulary; the minimum frequency controls which corpus terms survive.
    3. Distill the vocabulary against an operator-approved teacher model. The result is a static embedding model this server serves immediately, with no restart: select it on the Analyze tab, index with it, and search with it.

    Distillation is not gradient training. There are no epochs, no learning rate and no loss curve: the server runs each vocabulary row through the teacher once, reduces the result with PCA, and reweights the rows by frequency. Three things share the word vocabulary here: the teacher's own subword vocabulary, the vocabulary learned from your corpus in step 2, and the rows of the distilled model, which are the same terms.

    From code this is OpenNlpVocabularyService and OpenNlpModelTrainingService, or the gateway's POST /api/v1/import-dictionary, POST /api/v1/learn-vocabulary, and training endpoints; the Python quickstart's second example streams this whole flow.

    Save, watch coverage, retrain, rebuild

    Lifecycle

    Save live indexes to disk or make them read-only, point logical aliases at the current index, rebuild an index with a newly trained model while the old one keeps serving, and group live indexes into collections whose vocabulary coverage the server streams live.

    How to use lifecycle
    1. Save a live index to disk to keep it across server restarts, or make it read-only.
    2. Point a logical alias at the current index so clients keep one stable name while you swap the index behind it, blue/green style.
    3. Rebuild a live index with a newly distilled model, without changing its documents.
    4. Group live indexes into a collection to watch its vocabulary coverage live: the stream reports new terms that fall outside the current vocabulary artifact.

    From code these are the persist, seal, reindex, alias, and collection RPCs on OpenNlpSearchService, mirrored by the gateway's /api/v1/persist-index, /api/v1/seal-index, /api/v1/reindex-index, alias, and collection endpoints.

    Save and make read-only
    Save to disk writes the live index to disk, and it keeps accepting new documents. Make read-only writes it to disk too, and stops it accepting documents. It stays searchable, and this cannot be undone.

    Collections

    A collection is a named group of live indexes you want to watch together. It is not something you search. It records which indexes belong together, which dictionary, vocabulary and model they were built from, and how many unfamiliar terms should raise an alert; the server then reports, live, how much of the group's text the current vocabulary still covers. In Qdrant, Solr or Weaviate a collection is the searchable thing itself; here that is a live index.

    Leave this at 0 to never alert.

    Vocabulary coverage
    What vocabulary coverage measures

    A vocabulary here is the term list the serving model was distilled from (learned on the Trainer tab). Coverage is the share of term occurrences in the collection's indexes that hit a row of that vocabulary; the terms that miss are listed below as out-of-vocabulary. Falling coverage over time is vocabulary drift: the documents have moved on from the words the model knows. It does not measure semantic drift, where the same words change meaning. When coverage falls, learn a new vocabulary from the current documents, distil a new model, and rebuild the index with it.
